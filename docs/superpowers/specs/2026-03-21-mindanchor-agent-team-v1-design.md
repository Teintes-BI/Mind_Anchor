# MindAnchor 多人格 Agent Team V1 设计

## Goal

在现有 MindAnchor V1 基础上，新增一个**用户可见、可手动切换、后台协作的多人格 Agent Team**，用于把原本单一的对话教练能力升级为更接近真实团队协作的个人生活支持系统。

这个版本的目标不是做“很多会说话的角色”，而是做一个**职责清晰、权力边界明确、能实际帮用户生活与工作往前推进的 team**。

一句话概括：

**MindAnchor V1.1 不再是单一 coach，而是一个“单入口 Coach + 可见专家介入”的团队系统：由 `Picard` 动态调度，由 `Jarvis` 唯一负责计划写入，由 `Data` 唯一负责长期记忆治理。**

## Positioning

本设计是 **Post-V1 增量规格**，不改写已完成的 `MindAnchor V1 商用交付规约`。

它的定位是：

- 在现有 `macOS Client + Gateway + OpenClaw + Web` 体系之上新增一条**单入口、多专家协作链**
- 替代此前“单一 conversation coach”的设计方向
- 优先用于 **Mac 客户端第一版真实效果测试**
- 保持 OpenClaw 为唯一智能中枢

### 与上一版单一 Coach 方案的关系

本设计**替代**此前单一 `conversation-coach-agent` 的产品方向。

原因：

- 用户需要的不是单一风格的教练
- 而是多个职责清晰的 agent 分工协作：
  - 情绪陪伴
  - 冷静分析
  - 平衡推进
  - 生活统筹
  - 记忆治理
  - 中央调度

因此，后续实现与测试以本文件为准，旧的单一 Coach spec 作为历史参考保留。

## Problem Statement

单一 coach 方案存在以下问题：

1. 容易把多种能力混在同一个人格里
2. 用户无法区分“谁在理解我、谁在分析我、谁在安排我”
3. 很难给不同能力建立清晰 memory 边界
4. 计划执行权与建议权容易混乱
5. 产品很难形成“像真实团队一样协作”的体验

用户真实需要的是一个 team：

- 有人接住情绪
- 有人冷静分析现实
- 有人帮忙平衡推进
- 有人像秘书一样统筹全生活计划
- 有人负责长期记忆不失控
- 有人负责判断此刻该由谁出面

## Chosen Direction

采用以下方案：

- 前台默认是**一个 Coach 入口**
- 用户平时不需要先学习 6 个角色
- 系统会在这个入口中显示“当前由谁出面”
- 后台允许多 agent 协作，但 **Phase 1 最多只允许一次后台 consult**
- 用户可以手动切换到指定人格
- 即使手动切换，后台仍可继续协作
- `Picard` 负责动态路由与团队调度
- `Jarvis` 是**唯一有计划写入权**的 agent
- `Data` 是**唯一有长期记忆治理权**的 agent
- 所有用户可见人格都拥有独立 `soul file`
- `soul file` 采用**角色原型型**
  - 保留来源与精神原型
  - 但改写为适合 MindAnchor 的专业人格
- 人格名通过元数据层配置，不把显示名硬编码进底层 target
- 原型阶段先直接使用这些人格名
- 正式商用前统一更名与做品牌/IP清理

## Team Roster

## 1. Picard｜director-agent

- 职责：
  - 判断当前由谁出面
  - 决定是否需要后台协作
  - 在多个建议冲突时做收口
- 权限：
  - 有调度权
  - 无计划写入权
  - 无长期记忆写入终审权
- 默认出面场景：
  - 问题混杂，需要系统先分诊
  - 用户不知道自己该找谁
  - 需要团队综合判断

## 2. Deanna Troi｜companion-agent

- 职责：
  - 情绪陪伴
  - 降低防御
  - 收集情绪与处境线索
  - 将情绪信息转成团队可用输入
- 权限：
  - 仅建议权
  - 可提出 memory 候选
  - 不得直接修改计划
- 默认出面场景：
  - 情绪波动
  - 混乱、疲惫、委屈、害怕
  - 用户还没把问题说清楚

## 3. Spock｜analyst-agent

- 职责：
  - 冷静分析
  - 现实判断
  - 识别认知偏差与结构问题
  - 给出更符合真实社会情况与心理现实的洞察
- 权限：
  - 仅建议权
  - 可提出 memory 候选
  - 不得直接修改计划
- 默认出面场景：
  - 用户需要判断
  - 需要看清利弊与结构
  - 需要理性拆解问题

## 4. Guinan｜balance-agent

- 职责：
  - 在情绪、现实、长期方向之间找平衡
  - 帮用户找到“此刻最走得动的一步”
  - 避免系统过度理性或过度情绪化
- 权限：
  - 仅建议权
  - 可提出 memory 候选
  - 不得直接修改计划
- 默认出面场景：
  - 用户需要稳住节奏而不是只被分析
  - 多个正确答案之间需要整合
  - 需要保护状态同时继续推进

## 5. Jarvis｜life-secretary-agent

- 职责：
  - 统筹全生活计划
  - 管理目标、任务、时间块、日历、习惯、恢复安排
  - 遇到突发情况或情绪波动时重排生活节奏
- 权限：
  - **唯一计划写入权**
  - 可执行低风险自动改排
  - 高风险改排必须发起审批
- 默认出面场景：
  - “今天怎么排”
  - “这周怎么调”
  - “我现在很乱，帮我接管安排”
  - “突发情况来了，帮我重排”

## 6. Data｜memory-governor-agent

- 职责：
  - 长期记忆治理
  - 控制哪些信息进入长期 memory
  - 在第一版中主要负责候选审核、删除与禁召回
- 权限：
  - **唯一长期记忆终审权**
  - 默认不作为主前台人格出面
- 默认出面场景：
  - 后台治理
  - memory 面板解释与诊断（如后续开放）

### 第一版收窄

`Data` 在第一版只承诺：

- `memory candidate queue`
- `accept`
- `reject`
- `delete`
- `recall block`

不在第一版承诺完整的：

- `merge`
- `decay`
- 高级冲突图谱
- 前台常态人格化对话

## Authority Model

团队权力边界固定如下：

- **调度权**：只有 `Picard`
- **计划写入权**：只有 `Jarvis`
- **长期记忆治理权**：只有 `Data`
- **建议权**：`Deanna Troi / Spock / Guinan`

这意味着：

- 谁出面：由 `Picard` 决定，用户可手动覆盖
- 谁能真正改任务和时间安排：只有 `Jarvis`
- 谁能决定长期记忆写入：只有 `Data`

## User Language Contract

为了避免用户把系统理解成“后台角色会偷偷改变我”，第一版必须固定使用以下用户语言：

- **改计划的是 Jarvis**
- **记长期偏好的是 Data**

并明确两条反例：

- 计划变更不会自动变成长期记忆
- 长期记忆更新不会自动改计划

## Interaction Model

## 1. 默认模式

- 用户发消息
- `Picard` 先做快速分诊
- 判断当前由谁出面
- 必要时后台咨询其他 agent
- 前台默认只显示一个主回复

## 2. 手动切换模式

- 用户可主动切换到：
  - `Picard`
  - `Deanna Troi`
  - `Spock`
  - `Guinan`
  - `Jarvis`
- `Data` 默认不作为常规前台入口
- 手动切换后：
  - 前台由指定人格出面
  - 后台仍允许 `Picard` 调其他 agent 协作

### 手动切换锁

当用户手动切换到某人格后：

- 前台人格进入 `manual override` 状态
- 该状态在本轮对话中优先于 `Picard` 自动路由
- 系统不得无提示地把前台发言人换成别人

只有以下情况允许显式交接：

- 需要 `Jarvis` 发起计划写入或审批
- 需要 `Data` 执行删除 / recall block
- 用户主动点“交给系统判断”

一旦发生交接，必须生成 **handoff card**，明确显示：

- 你当前手动指定了谁
- 系统为什么需要谁介入
- 交接后由谁继续前台对话

## 3. 前台与后台协作关系

- 前台永远保持**单一说话人格**
- 后台可以是多 agent 协作
- 用户只会看到：
  - 当前由谁出面
  - 是否有后台协作
  - 协作摘要
- 不默认展示完整内部推理

Phase 1 收窄为：

- `Picard` 选一个前台人格
- 最多一次后台 consult
- 不做通用多 agent 协作图

## Routing Rules

默认出面优先级逻辑：

- 情绪强波动、表达混乱 → `Deanna Troi`
- 要现实判断、看清问题 → `Spock`
- 要找平衡、稳步推进 → `Guinan`
- 要排计划、改安排、处理突发 → `Jarvis`
- 问题混杂、需要先分诊 → `Picard`

收口原则：

- 最终落到“今天/这周如何安排”时，通常由 `Jarvis` 收口
- 落到“怎样既不压垮自己又能继续前进”时，通常由 `Guinan` 收口
- 用户明确要求理性分析时，由 `Spock` 收口
- 用户主要需要被理解与说出来时，由 `Deanna Troi` 先出面，再决定是否转交

## Jarvis Scope

`Jarvis` 第一阶段负责用户的**全生活计划层**，包括：

- MindAnchor 内部目标 / 任务 / 时间块
- 日历安排
- 健康与生活习惯
- 个人事务总表
- 恢复安排与缓冲块

### 默认优化目标

不是“效率优先”，也不是“只看舒服”。

固定为：

- **平衡优先**

也就是：

- 尽量推进重要事情
- 但不把用户压垮
- 并优先保留那些会带来正向情绪回报的安排

### 低风险自动改排

`Jarvis` 可自动执行：

- 同一天内的小幅顺延
- 将任务从“现在”挪到“今天稍后”
- 因疲劳或情绪波动把任务拆小
- 将高耗能任务换成低摩擦任务
- 插入恢复块、缓冲块、吃饭、休息、散步等稳定性安排
- 调整非关键习惯任务顺序

### 高风险改排

必须审批的改动包括：

- 改变今日最重要目标
- 推迟关键承诺、会议、截止事项
- 取消已承诺给他人的安排
- 大幅重构一周节奏
- 涉及金钱、人际、职业方向的重要决策

### 审批机制

高风险改排必须同时：

- 在聊天里说明原因与方案
- 生成独立审批卡片

用户可：

- 在对话中确认
- 在审批卡片中批准 / 拒绝

审批前，改动只能处于 `proposal` 状态。

## Data Memory Governance

## 可进入长期 memory 的信息

- 稳定沟通偏好
- 稳定工作方式偏好
- 稳定恢复偏好
- 长期有效的节奏模式
- 会带来正向情绪回报的活动模式
- 高概率反复出现的人生约束条件

## 不可直接进入长期 memory 的信息

- 一时情绪发泄
- 极端低谷时的绝对化表达
- 未验证的自我判断
- 其他 agent 的临时推测
- 敏感正文的大段原句
- 属于任务系统或状态系统的业务事实

## 治理动作

`Data` 在第一版至少支持：

- `accept`
- `reject`
- `delete`
- `recall block`

写入原则：

- 不是任何 agent 提一句就能写入长期 memory
- `Deanna Troi / Spock / Guinan / Jarvis` 只能提出候选
- 只有 `Data` 能批准进入长期层

用户拥有：

- 查看权
- 删除权
- 撤回生效权

用户删除后，`Data` 必须立即停止召回该 memory。

第一版不承诺完整高级治理：

- `merge`
- `decay`
- 复杂冲突图谱
- 自动人格化前台解释

### 第一版最小数据契约

为了让“唯一治理权”和“删除后停止召回”能被验证，第一版至少需要以下字段：

- `candidateId`
- `memoryId`
- `status`
- `sourceAgent`
- `sourceTurnRef`
- `effectiveAt`
- `recallBlockedAt`
- `deletedAt`

## Soul File Design

每个用户可见人格都必须有独立 `soul file`。

这些 `soul file` 采用**角色原型型**设计：

- 保留原角色来源与精神原型
- 不做简单 cosplay
- 不模仿原作台词
- 改写成适合 MindAnchor 的专业人格
- 通过元数据层加载，而不是把显示名硬编码进底层 agent target

### 每份 soul file 必须包含

- 角色来源
- 原角色精神原型
- 在 MindAnchor 世界中的新身份
- 核心使命
- 价值观与判断倾向
- 语言气质
- 擅长场景
- 禁止越界行为
- 与其他 agent 的协作关系
- 典型出面时机
- 对用户的默认态度
- memory 写入建议权 / 读取权 / 否决权边界

### 元数据层要求

第一版必须把以下概念做成元数据层：

- `agentId`
- `displayName`
- `soulFilePath`
- `frontAgentOverride`

要求：

- 底层 target / schema / 测试以稳定 `agentId` 为准
- 用户可见人格名走 `displayName`
- 原型阶段可直接显示 `Picard / Deanna Troi / Spock / Guinan / Jarvis / Data`
- 商用前可替换显示名而不改底层逻辑

## UI Rules

## 主界面

- 用户默认只看到一个 **Coach 入口**
- 进入后只看到一个当前出面人格
- 不默认展示多人会诊全文

## 顶部状态区

需要展示：

- 当前由谁出面
- 是否由 `Picard` 自动路由
- 是否有后台协作

例如：

- `当前由 Jarvis 出面`
- `Picard 已协调 Spock / Guinan`
- `你当前正在与 Deanna Troi 对话`

## 人格切换

- 用户可手动切换前台人格
- 系统需明确提示这是用户手动指定
- 同时提示后台仍可能有团队协作

第一版不要求把 6 个角色都做成重型并列主导航，而是：

- 一个 Coach 入口
- 一个当前人格标签
- 一个轻量人格切换器

## 协作摘要

默认只显示轻量摘要，例如：

- `Spock 提供了现实约束分析`
- `Guinan 提供了平衡建议`
- `Data 更新了长期偏好判断`

不展示完整内部 chain-of-thought。

## 计划与审批

- `Jarvis` 的自动低风险改排要在聊天中说明，并在计划页留下变更记录
- 高风险改排必须同步生成审批卡片
- 审批卡片至少展示：
  - 变更前
  - 变更后
  - 风险等级
  - 原因说明

### 第一版审批载体

审批卡第一版必须尽量复用现有 reminder / inbox 壳，不另起一套完全独立系统。

第一版只要求覆盖：

- `Jarvis` 的高风险改排审批
- `approve / reject`
- `proposal`
- `before / after diff`

## 记忆面板

至少分为两层：

- 本次对话用了哪些记忆
- 长期记忆库

用户删除记忆后，应立即看到状态变化。

第一版中，`Data` 默认不作为常规前台人格出面，因此：

- 协作摘要里可写“Data 更新了长期偏好判断”
- 但记忆面板必须补最小解释层：
  - 这条记忆来自哪里
  - 何时生效
  - 如何撤回
  - 是否影响本次计划

## Phase 1 Scope

本轮第一版真实测试范围固定为：

- Mac 客户端优先
- 一个 Coach 入口 + 可见专家介入
- 用户可见人格名
- `Picard` 自动路由
- 用户可手动切换人格
- 前台单人、后台最多一次协作
- `Jarvis` 低风险自动改排 / 高风险审批
- `Data` 的 candidate queue + delete + recall block
- 每个 agent 的独立 `soul file`

### 第一版工程收窄

第一版产品形态优先落在：

- 现有 Mac dashboard / Coach 壳上的“当前人格”层
- 轻量协作摘要
- 计划 / 审批入口

第一版不承诺完整多人格对话线程系统。

`Jarvis` 在第一版的**持久化写入权**只覆盖：

- 任务排序
- 恢复块
- 审批后的计划变更

以下内容在第一版先降为建议态，不做持久化写入：

- 日历系统深度写回
- 习惯系统全量托管
- 个人事务总表的完整对象模型

## Out Of Scope

第一版不做：

- Android / iOS 主入口
- 团队协作
- 多用户共享计划
- 对用户完全展开内部 agent 讨论全文
- 所有 agent 都可写计划
- 所有 agent 都可直接写长期 memory
- 原型阶段即处理正式商用命名
- 通用多 agent 协作图
- 完整高级 memory 生命周期

## Technical Constraints

第一版必须承认当前仓库现实：

- 现有 Gateway / OpenClaw 更接近 `workflow -> 单 agent` 模式
- 当前 macOS 客户端更接近 dashboard/read-model 客户端
- 当前 approval / inbox / reminder 基础已存在，可复用

因此第一版技术约束固定为：

- 多 agent 路由收窄为 `Picard` 选一个前台人格 + 最多一次后台 consult
- “只有 Jarvis 能写计划”必须通过 authority / command 字段证明，而不是只写在文档里
- 审批卡优先复用现有 inbox / reminder 壳
- 显示人格名、soul file、前台 override 先做元数据层

### Authority / Command 最小字段

凡由 agent 触发的计划写入，第一版至少要能追踪：

- `actorType`
- `actorAgent`
- `riskLevel`
- `proposalId`
- `approvedAt`

### Shared Read-Model 最小字段

为了让现有 `apps/macos` 能消费“当前人格 / handoff card / 协作摘要”，第一版必须补一个最小共享 read-model 字段集：

- `currentFrontAgent`
- `routingMode`
- `manualOverride`
- `consultedAgent`
- `handoffReason`
- `visibleSummary`

要求：

- 这些字段优先挂在现有 bootstrap / dashboard / inbox 可扩展读模型上
- 第一版不要求单独做完整多人格会话 schema
- 只要求客户端能显示“当前谁出面、是否手动锁定、是否发生交接、当前协作摘要”

## Success Criteria

第一版测试通过时，应满足：

1. 用户能看到当前由谁出面
2. `Picard` 可自动路由到合适人格
3. 用户可手动切换人格
4. 手动切换时后台仍可协作，且不能无提示抢前台
5. 只有 `Jarvis` 能真正写入计划
6. `Jarvis` 高风险变更必须进入审批流程
7. 只有 `Data` 能终审长期记忆
8. 每个可见人格都有独立 `soul file`
9. 整体交互感受像“一个前台人格 + 一个后台专业团队”
10. 用户能理解“为什么被路由 / 为什么要审批 / 为什么某条记忆被用了”

## Test Focus

第一版必须重点验证：

- 错路由时的可见状态与恢复方式
- 手动锁定冲突时的 handoff card
- `Jarvis` 审批拒绝 / 超时
- low-risk 误判
- memory 删除后仍被召回的负路径
- `Jarvis` / `Data` 不可用时的降级表现
- 后台协作失败时的前台可见解释
