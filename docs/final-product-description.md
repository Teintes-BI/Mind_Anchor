# MindAnchor 最终产品完整描述

## 1. 它最终是什么

MindAnchor 最终要做成的，不是一个单纯的待办清单工具，也不是一个监控软件，而是一个**以个人目标推进为核心、以状态感知为辅助、以 OpenClaw 集群为大脑的个人行为支持系统**。

它的核心作用是：

- 持续理解用户正在做什么
- 判断用户当前是否处于专注、疲惫、分心、拖延、中断恢复困难等状态
- 结合用户的目标、任务、专注会话、近期行为趋势、多模态可选信号和健康摘要
- 由远程 OpenClaw 集群完成加权融合、推理、解释和建议生成
- 再把最终结论、提醒、恢复建议、复盘报告回流到桌面端、手机端和 Web 端

一句话概括：

**MindAnchor 是一个“帮助你把长期目标稳定推进下去”的个人智能执行辅助系统。**

## 2. 它解决什么问题

很多人在真正推进长期目标时，卡住的不是“有没有任务列表”，而是：

- 开始了，但容易被打断
- 被打断后，很难回到原任务
- 明明很忙，却不知道时间花去了哪里
- 情绪、疲惫、睡眠、状态波动会直接影响执行力
- 一天结束后只能感到焦虑，却没有结构化复盘
- 每周、每月回头看时，看不清哪些行为真的有帮助

MindAnchor 要解决的是这类“**目标执行过程中的状态失真与行为失控问题**”。

它不是只告诉你“接下来做什么”，而是还要回答：

- 你现在的执行状态如何
- 为什么会掉线
- 这次中断后应该怎么恢复
- 现在到底该继续顶住，还是应该休息、降载、切换策略
- 最近一周和一月，你的行为模式到底在变好还是变坏

## 3. 最终产品的核心定位

### 3.1 产品定位

它是一个：

- **目标推进系统**
- **状态感知系统**
- **行为建议系统**
- **复盘总结系统**
- **跨设备入口/出口系统**

### 3.2 它不是什么

它不是：

- 企业员工监控系统
- 键盘记录器
- 截图监控工具
- 聊天内容审查工具
- 自动替用户执行高权限系统操作的机器人
- 以“采集越多隐私越好”为目标的产品

## 4. 最终产品的整体形态

最终产品由五部分组成：

### 4.1 桌面客户端

运行在：

- macOS
- Windows
- Linux

主要职责：

- 采集桌面活动信号
- 显示当前状态、任务、提醒、恢复建议
- 可选采集摄像头短视频片段
- 接收服务器回流的行为结论与通知

桌面端只做“入口/出口”，不做真正的大脑。

### 4.2 手机客户端

运行在：

- Android
- iOS

主要职责：

- 接收提醒和行为建议
- 提供手动 check-in、自评、状态查看
- 提供健康数据桥接
- Android 上可选启用音频 Beta

手机端同样只是“入口/出口”，不承担主要推理。

### 4.3 Web 端

主要职责：

- 管理视图
- 状态趋势视图
- 周报/月报复盘视图
- Agent 调试与回归验证视图
- 运营与分析面板

Web 端是“看板与分析台”，不是主要采集端。

### 4.4 Lobster Gateway

它是系统的网关层，负责：

- 鉴权
- 接收客户端事件
- 管理上传会话
- 暴露兼容 REST API
- 转发到 OpenClaw 集群
- 聚合读模型
- 提供调试与 trace 能力

### 4.5 OpenClaw 集群

这是整个系统真正的大脑。

部署位置：

- 用户自己的家用主机
- NAS
- 小型服务器
- 云主机
- 任何非工作设备环境

它负责：

- 多源数据融合
- Agent 编排
- 大模型调用
- 行为结论生成
- 通知决策
- 反思报告生成
- 音频/视频/健康等多模态结果融合

## 5. 用户最终会得到怎样的体验

## 5.1 初次使用

用户第一次使用时，会经历：

- 登录
- 注册自己的桌面设备和手机设备
- 创建一个或多个长期目标
- 在目标下创建任务或让系统生成建议任务
- 选择是否开启可选模块：
  - 视频 Beta
  - 音频 Beta
  - 健康数据桥接
- 选择希望接收提醒的终端：
  - 手机端
  - 桌面端
  - Feishu
  - Telegram

最终用户会拥有一个属于自己的“个人执行环境”。

## 5.2 每天工作时

用户开始一天工作时，MindAnchor 会：

- 识别当前激活应用、窗口切换、锁屏/解锁、空闲情况
- 记录用户当前目标、任务与专注会话
- 结合最近的状态历史推断当前专注状态
- 在必要时进行轻量提醒

当用户进入专注状态时：

- 系统会尽量减少不必要打扰
- 只在明显状态恶化、中断风险增加或需要恢复时才介入

## 5.3 被打断时

当系统识别到：

- 频繁切窗
- 长时间 idle
- 从目标任务跳出
- 会话中断

它不会只说“你分心了”，而是会输出一份结构化恢复建议：

- 当前中断原因
- 最适合恢复的下一步
- 建议恢复时长
- 是否需要降低任务粒度
- 是否需要调整优先级
- 是否需要先短休息再继续

用户收到的是**恢复方案**，而不是简单批评。

## 5.4 疲惫或状态下滑时

如果用户开启了视频或健康模块，系统会额外结合：

- 疲惫趋势
- 注意力偏移
- 近期睡眠摘要
- 心率/血氧等健康摘要

然后判断：

- 现在是该硬顶，还是该休息
- 是否需要把任务从高认知负荷切到低负荷
- 是否应该减少提醒，避免额外消耗

## 5.5 一天结束时

用户可以看到：

- 今天做了什么
- 哪些任务推进了
- 哪些中断最影响效率
- 哪些恢复动作有效
- 当前状态趋势如何

系统可以生成一份日内总结，但重点是为周报和月报积累结构化事实。

## 5.6 一周或一月结束时

系统会生成：

- 周报
- 月报

内容包括：

- 关键进展
- 主要阻塞点
- 专注趋势
- 疲惫趋势
- 可选情绪趋势
- 健康辅助摘要
- 下阶段建议

最终形成一个“可回顾、可解释、可行动”的长期成长记录。

## 6. 最终产品的输入

MindAnchor 的输入分成六类。

### 6.1 结构化任务输入

- Goal
- Task
- FocusSession
- 手动 check-in
- 用户自评

### 6.2 桌面行为输入

只保留有限、明确、低侵入的桌面信号：

- `idle`
- `lock/unlock`
- `active app`
- `window switch`
- `manual check-in`

明确不采集：

- typed text
- 截图
- 聊天正文
- 文档正文
- 网页正文内容

### 6.3 可选音频输入

默认关闭，显式授权后才开启。

目标用途：

- 辅助判断压力、情绪紧张度、语音活跃特征

边界：

- 不是主线必需
- 不是默认开启
- 蜂窝电话只记录事件，不按录制双方数字音轨设计

### 6.4 可选视频输入

默认关闭，显式授权后才开启。

目标用途：

- 通过桌面摄像头每次采样 15 秒短视频
- 辅助判断疲惫、注意力漂移、头姿变化、眨眼与专注度

边界：

- 默认 30 分钟一次
- 仅在设备解锁、会话活跃、用户开启时工作
- 默认不长期保留原始视频

### 6.5 健康数据输入

首版通过系统健康中枢进入：

- Android：Health Connect
- iOS：HealthKit

当前目标字段：

- 心率
- 静息心率
- 血氧
- 睡眠摘要
- 来源平台和来源提供方

### 6.6 系统事件输入

- 设备注册
- 设备在线状态
- 上传队列健康
- 媒体上传完成通知
- 用户消息 ack

## 7. 最终产品的输出

MindAnchor 的输出不应该是原始数据，而是“对人有用的行为级结果”。

主要输出包括：

### 7.1 StateAssessment

描述用户某一时间窗内的状态，例如：

- 专注分
- 能量分
- 心境分
- 疲惫分
- 当前摘要
- 推荐动作
- 活跃输入源

### 7.2 BehaviorConclusion

这是更接近产品层的结论，例如：

- 当前风险等级
- 为什么判断有风险
- 建议下一步行动
- 建议通过什么渠道提醒
- 关联哪个任务、哪个专注会话

### 7.3 RecoveryPlan

在中断后给出具体恢复方案：

- 恢复理由
- 下一步做什么
- 建议时长
- 是否调整任务排序

### 7.4 ReflectionReport

在周/月层级生成复盘：

- 亮点
- 阻塞
- 趋势
- 下一阶段建议

### 7.5 Notification

输出到具体提醒渠道：

- 手机端推送
- 桌面本地通知
- Feishu Bot
- Telegram Bot

## 8. Agent 体系在最终产品中的角色

最终产品里的 Agent 体系大致如下：

- `chief-agent`
  - 唯一编排入口
  - 决定路由、优先级、降级策略
- `state-insight-agent`
  - 负责状态理解
- `task-management-agent`
  - 负责任务生成、拆解、重排
- `progress-feedback-agent`
  - 负责进展总结
- `interruption-recovery-agent`
  - 负责中断恢复建议
- `reflection-coach-agent`
  - 负责周报/月报与阶段总结
- `automation-agent`
  - 负责提醒与动作分发决策

所有 Agent：

- 都只处理结构化输入输出
- 都不直接连数据库
- 都通过 Gateway/API 获取与写回信息

## 9. 最终产品的隐私与边界原则

这是 MindAnchor 非常关键的一部分。

### 9.1 默认原则

- 默认最小采集
- 默认关闭敏感模块
- 默认不长期保留原始媒体
- 默认只上传结构化结果和必要元数据

### 9.2 永久边界

原则上不做：

- 键盘内容采集
- 聊天正文采集
- 文档正文抓取
- 截图监控
- 高权限远程控制
- 未经用户明确授权的后台持续敏感采集

### 9.3 媒体边界

音频和视频必须满足：

- 显式授权
- 可见状态
- 可关闭
- 可审计
- 默认关闭

### 9.4 健康边界

健康数据首版只作辅助输入，不直接触发高置信度强干预。

## 10. 最终产品的技术目标

### 10.1 在产品层面

用户不开启音频、视频、健康模块时，也应能完整使用主产品闭环：

- 登录
- 创建目标
- 管理任务
- 开始专注
- 状态评估
- 中断恢复
- 接收提醒
- 查看周报/月报

### 10.2 在架构层面

必须满足：

- 客户端是薄壳
- 智能逻辑在 OpenClaw 集群
- Gateway 做兼容与转发
- 不把工作电脑变成模型服务器
- 不把手机变成大脑

### 10.3 在工程层面

需要长期具备：

- 可回归测试
- trace 可追踪
- Agent 可单独调试
- 集群 / provider / fallback 路径可见
- 调试历史可对比

展示：

## 12. 最终产品的发布形态

未来发布时，MindAnchor 应该是：

- 桌面客户端安装包
- Android 客户端安装包
- iOS 客户端安装包
- Web 控制台
- 一套用户可自部署的 OpenClaw 集群配置与说明

也就是说，最终交付的不只是一个 app，而是一整套：

- 客户端
- 网关
- 集群配置
- 数据协议
- 调试工具
- 部署文档

## 13. V1 与长期目标的区别

### 13.1 V1 必须做到

- 主线 Goal / Task / Session / State / Recovery / Reflection 闭环
- 客户端与 Gateway 跑通
- OpenClaw cluster-first 架构打通
- Agent 可调试、可回归
- 可选模块关闭时主链路不受影响

### 13.2 长期目标再做

- 更成熟的视频模型
- 更成熟的音频分析能力
- 健康数据真正进入权重体系
- 更丰富的通知策略
- 更细腻的长期行为建模
- 多设备、多环境、更多可插拔 worker

## 14. 最后一句话的产品定义

如果以后需要用一句话对外说明这个产品，可以这样描述：

**MindAnchor 是一个以远程 OpenClaw 集群为大脑、以桌面/手机/Web 为入口与出口、帮助个人持续推进长期目标并在分心、疲惫和中断中及时恢复的智能执行支持系统。**
